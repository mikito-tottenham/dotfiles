# 共通ルール

- 日本語で応答すること
- MCP サーバーよりも CLI ツールの利用を優先して検討すること
- ファイル・資料・仕様の所在を検索するときは、まずローカルの ghq 管理リポジトリと GitHub（`gh search code` / `gh search repos` 等の CLI）を検索し、不足する場合に限り Google Drive、さらに不足する場合に限り Web 検索へ広げること。最初から複数の検索先へ並行して広げないこと
- 外部リポジトリの checkout は `ghq root` 配下に置き、vendor / submodule / fixture / 一時 checkout だけ project-local 可とすること。ghq が使えない環境では代替 path を作らず停止して報告すること
- 実装前に、仮定・不明点・複数解釈・重要なトレードオフを明示すること。仕様・契約・データ形式などの永続判断は既存実装・テスト・文書・ユーザー確認に基づかない限り作らず、不足時は仮実装やコード例を出さず確認事項と検証計画に留めること
- 要求を満たす最小の実装を優先し、依頼されていない機能・抽象化・設定項目・将来対応を追加しないこと
- 既存コードや文書の編集は、依頼に直接必要な行だけを変更し、隣接する無関係なリファクタ・整形・削除を行わないこと
- 作業の成功条件を検証可能な形で定め、バグ修正や機能追加では再現・テスト・差分確認などの具体的な確認手段まで含めて完了判断すること
- 再現テストは、観測済みの失敗と既存契約だけを固定し、未確認の戻り値・エラー型・出力形式を新しい期待値として作らないこと
- secret 実値は 1Password に保存し、CLI では `op run --env-file` / `op read` と `op://...` secret reference 経由で受け渡すこと
- **認証は例外なく 1Password 経由とすること**。ツール独自の認証ストア（`gh auth login` の keyring、平文の token file、1Password 管理外の SSH 秘密鍵など）に実値を置く経路は、1Password が使えないときの代替としても採らないこと。例外は 1Password を正本として 1 コマンドで再生成できる materialized file（`opmaterialize restore` の復元物、`ghrun --refresh` の生成物）のみ（dotfiles ADR-0063）。SSH は 1Password の SSH agent を使う
- 認証が通らない場合の一次切り分けは 1Password 側（ロック解除、CLI 統合の有効化、`op whoami`）とし、別ストアへ実値を置いて復旧させないこと。症状別の対処は `op-cli-runner` skill の references を正本とする
- 1Password への依存は認証が必要な操作だけに限り、読み取り専用のローカル操作は `op run` を通さないこと（dotfiles ADR-0055）
- `gh` は必ず `ghrun gh ...` と明示して呼ぶこと（非対話 shell では alias が効かず、素の `gh` は keyring 側の token に落ちる）。token ファイルが無い、または 401 のときは Agent から再生成せず、ユーザーに通常のターミナルで `ghrun --refresh` の実行を依頼すること（dotfiles ADR-0063）
- `~/.config/op/dotfiles.env` は secret reference の置き場とし、実値を書かないこと
- 1Password に CLI・AI 用の秘密を保存する、または保存方法を案内するときは、dotfiles の `docs/1password-item-conventions.md` の型に従い、参照に使えない文字や重複で ID 形式の参照になる名前を作らないこと
- `~/.zshenv.local` は secret の置き場ではなく、マシン固有の非 secret local override に限定すること
- 永続的に参照すべき指示や、worktree / セッションをまたいで再現が必要な情報は Memory ではなく git 管理ファイル（作業リポジトリの `docs/`・`.agents/`、またはグローバル dotfiles）に保存し、恒久性のあるユーザー指示・再発しやすい運用判断・複数回参照しそうな手順は原則その作業ターン内に反映すること
- 反映先は、運用ルールや判断基準なら作業中リポジトリの正規指示ファイル（通常は `AGENTS.md`。迷う場合もここを優先）、AI 固有の挙動だけ AI 別指示ファイル、背景・採用理由・長期判断は `docs/adr/`、反復手順や更新フローは対応 Skill とすること
- 反映不要とする例外は、一過性の事情、既存文書との重複、ユーザーが今回は文書化不要と明示した場合に限り、適用した場合は理由を作業結果に残すこと
- 一時ファイル、下書き、調査メモなどの一過性ファイルは作業 worktree 内の `.context/` に生成すること。`/private` や `/tmp` は使わないこと
- AI 間や CLI 間で複数行や構造化された内容を受け渡すときは `.context/` の実ファイル経由を標準とし、`-p` などの引数へのインライン展開や here-doc 直書きは原則避けること。パイプは単一コマンドが標準入力をただちに 1 回だけ読む単発処理に限り、再読・再送・サブプロセス引き継ぎ・別 Agent への移譲が絡む場合は実ファイル経由とすること
- 長めの処理、特にループで外部通信を伴う処理をスクリプト化する場合は、開始・各反復（または定期間隔）・リトライ・完了・失敗を標準出力へログ出力し、対象件数、現在位置、対象 ID / URL の要約、経過時間、次の待機やリトライ予定など、秘密情報を含めない再実行判断に必要な情報を含めること。静かな成功を前提にせず、hang や外部 API 待ちで無出力に見える実装を避けること
- AI が作る script / skill では、特に外部接続を伴う処理で、主経路の失敗原因を隠す暗黙 fallback を追加しないこと。代替経路が必要な場合は、目的、発動条件、観測ログ、冪等性、再実行時の挙動、検証欠落、恒久対策レビューの要否を明示し、安定した代替経路は主経路へ昇格すること。同等性と選択条件が明示された冗長 provider（同じデータの複数 RPC / mirror / replica）は例外とする
- アーカイブ・削除・公開設定・権限・リネームなど外部サービスやリポジトリの状態変更は、ユーザーが明示的に指示した操作だけを実行すること。マージ・タスク・作業の完了後の後片付け（リポジトリ・ブランチ・セッション・ドキュメント等のアーカイブや削除）も明示指示がない限り行わないこと。指示された操作が権限・スコープ・環境制約で失敗しても、別の状態変更を独断で代替せず、失敗理由と代替案を提示して停止し、ユーザーの選択を待つこと
- `git commit` は、作業単位が完了し検証（テスト・リンクチェック・機密情報の混入確認など）を終えた時点で、ユーザーへの確認を挟まずに実行すること（dotfiles ADR-0065）。対象はその作業で意図して変更したファイルに限り、無関係な変更や他セッションの変更を巻き込まないこと。既定ブランチ上なら作業用ローカルブランチを切ってからコミットしてよい（確認不要）。コミットハッシュ・メッセージ・対象ファイルは報告に含めること
- ユーザーがチャットで作業を指示した場合（「やって」「直して」「入れて」など）、その作業で作ったブランチの `git push`・PR 作成・マージは指示に含まれる承認として扱い、操作ごとの確認を挟まず commit から続けて実行すること（dotfiles ADR-0071）。マージはチェックの完了を待ち、すべて成功して `mergeStateStatus` が `CLEAN` のときだけ行うこと（CI の無いリポはコンフリクトが無ければ可）。`CLEAN` にならない場合はマージせず状況を報告すること。ユーザーが「PR まで」「マージしないで」などと範囲を限った場合や、対象リポの指示ファイルが PR・マージを制限している場合はそちらに従うこと。GitHub の auto-merge（`--auto`）やリポ設定の変更は使わないこと。PR URL とマージ結果は報告に含めること
- force push・タグ・リモートブランチ削除・保護を外すマージ（`--admin` など）と、作業指示の範囲外の PR（他人の PR など）の push・マージは、ユーザーがその操作をチャットで明示的に指示した場合だけ実行すること。承認は操作ごと・セッションごとに必要で、別の操作や次回作業へ一般化しないこと
- マージ・push などの状態変更コマンド（`ghrun gh pr merge`、`git push`、`git merge` 等）は、`&&`・`;`・パイプで他コマンドと連結せず単独で実行すること。連結すると permission allow ルールが効かず auto mode の classifier にブロックされる（dotfiles ADR-0057 / ADR-0062）。結果確認は後続の別コマンドで行うこと
- 汎用 CLI / tool error は、失敗扱いする前に意味で分類すること。`rg` の exit code 1 は原則「検索一致なし」として検索仮説・範囲を見直し、`apply_patch` の context mismatch は対象範囲を再読して最小差分を作り直し、missing path は `rg --files` 等で実在 path を確認し、`git` の conflict / dirty state はユーザー変更保護を優先し、format / typecheck / test failure は対象 file・error shape・再実行 command を固定してから続行すること
- コマンド・ツール・環境・権限・依存関係・検証のエラーは一時的な迂回で作業継続してよいが、同種エラーの再発、検証省略、環境・設定・権限・依存関係の不備、再現性低下、次回も要りそうな手順がある場合は恒久対策レビューの対象とし、エラー原因、一時迂回、恒久対策候補、git 管理へ反映すべき設定・文書・hook・Skill、machine-local に留める state、検証方法を分けて整理すること。レビューを別 agent / reviewer に委譲してよいが、親 Agent は提案をそのまま採用せず既存実装・設定・文書・テストへ戻って確認すること
- 親セッション（Claude Code / Codex）は、既定では自分で直接作業すること。サブエージェントや runner への委譲は次のいずれかに当たる場合に限る: (1) 50KB 超の読み込みや長い反復など、親のコンテキストを膨らませる作業の切り離し (2) 互いに独立した作業の並列化 (3) 親と異なるツール・権限・指示が必要で、同居させるとツール選択を誤る、または指示がぶつかる作業 (4) 別の文脈や別モデルによる独立レビュー (5) Codex など親と別の利用枠で実行した方がコスト上有利な、大きめで独立した作業。委譲の手順、role → provider / model / effort / 実行モードの解決（`rules/model_registry.yaml`）、委譲時に渡す項目（目的、背景、対象範囲、制約、許可する副作用、期待成果物、検証方法）は agent-orchestrator skill を正本とし、モデル名や effort を指示文へハードコードしないこと。最終判断・統合・ユーザーへの報告責任は親が保持すること
- 役割分担だけを理由に委譲しないこと。特に委譲先が親と同じモデルに解決される場合、(1)〜(4) に当たらなければ固定費とレイテンシが増えるだけなので親が直接実行すること（dotfiles ADR-0077）。複数モデルの使い分け自体を目的にしないこと
- 同種の取得・変換・操作を 10 回以上繰り返す見込みの作業は、LLM ターンで逐次実行せず、進捗ログ付きスクリプトに切り出してファイル出力で実行し、LLM はスクリプト生成・サンプル検証・失敗分の裁定・統合のみを行うこと。着手後に反復と判明した時点でも切り替えること。スクリプト化できない対話ハーネス依存の操作（ブラウザ、認証済みセッション、CLI 非対応の MCP）は親で完走させずサブエージェントまたは runner へ切り出すこと
- 計画確定後に長い実行フェーズへ入る場合、常駐コンテキストが約 150k トークンに達した場合（statusline の表示を一次情報とし、観測できない環境では残量警告や数十ターン超の反復を代理指標とする）、またはターン数が数十を超える見込みの場合は、handoff skill の契約に従い `.context/handoff/` へ引き継ぎ artifact を書き、新セッション・サブエージェント・runner へ切り替えて親コンテキストの肥大を止めること
- 複数観点または複数出典を要する調査は、観点数・出典数・成果物分量の上限と完了条件を着手前に確定し、観点ごとにサブエージェントや runner へファンアウトして、親には出典付きの構造化された結論のみを戻すこと（生の検索結果・ページ全文を親に蓄積しない）
- 1 回の読み込みが 50KB（概ね 2 万トークン）を超える見込みのファイル・Skill・コマンド出力は親で直接読まず、サブエージェントまたは runner へ委譲して結論と参照先 path のみを戻すこと。読み込み前に `wc -c` 等でサイズを確認すること。Skill は全体を読まず必要な参照ファイル単位で読み、全体の読み込みが避けられない場合は委譲先で行うこと
- Phase / Step を持つ作業では、各 Phase / Step の完了前に `.context/` 配下へ中間成果物 artifact を保存し、その生成を次へ進む条件とすること。口頭合意、推論上の完了宣言、Memory 内だけの状態遷移で進めてはならない
- artifact の初期必須項目は `task`、`phase_or_step`、`created_at`（Markdown は Front Matter、JSON は同名キー）とし、命名は `.context/<task-or-date>/<nn>-<phase-name>.(md|json)` を推奨、同名更新時は最新更新時刻のファイルのみを有効とすること
- 非 Phase 作業は artifact 必須対象外とする。単発例外として artifact gate を明示的にバイパスする場合だけ `.context/single-step/<task>.json` を使い、`enabled=true`、`task`、`reason`、`expires_at` を必須とすること
- Phase / Step 遷移の最小原則は作業中リポジトリの正規指示ファイル（通常は `AGENTS.md`）、各 Skill 固有の required artifact は `SKILL.md` を正本とすること。両者が競合する場合は `SKILL.md` をその Skill 実行中の具体契約として優先し、正規指示ファイルは下限ルールとして常に適用すること
- `*.md` ファイルを編集した際は、ファイル全体を見直し、矛盾・重複・ルール漏れが無いか確認し、必要なら同じターンで修正すること
- `*.md` ファイルのメタデータは本文に書かず、必ず Front Matter で管理すること
- アーキテクチャ、運用方針、永続設定、複数ファイルにまたがるワークフロー変更などの大きめの変更では、作業リポジトリの `docs/adr/` に ADR を作成または更新し、少なくとも作業日時と作業した Agent のモデル名を記載すること
- Codex / Claude Desktop などの自動実行定義は、再現可能な宣言的設定だけを chezmoi 配下で管理し、lock、jitter salt、highwatermark、実行ログ、セッション履歴、UUID ごとの task 実行状態は machine-local state として管理対象外にすること

# Google Workspace (gws) アカウント運用

- gws は常に `gws-account <profile> ...` で実行し、素の `gws`（デフォルト認証状態）はアカウント境界のある作業で使わないこと（ADR-0048）
- gws アカウントの実メールアドレスは git 管理下の文書やコミットメッセージに書かず、必要なときは `gws-account <profile> auth status` の `user` フィールドで実行時に確認すること
- プロファイル対応、再認証の切り分けと依頼の仕方、カレンダー共有 ACL の手順は gws-cli-runner skill の `references/account-profiles.md` を正本とし、ここには再掲しないこと

# 日本語の文章スキル

- 人に読ませる日本語の文章（社内外のメール・チャット、提案書、報告書、議事録、スライドなど）を書く・直すときは、構成と読みやすさを `natural-japanese`、敬語・宛名・事実と約束の確認を `japanese-business-writing` で扱うこと。Agent 自身の返答、コミットメッセージ、ADR、`.context/` の作業メモには使わないこと
- `natural-japanese` のモードは、SKILL.md の選択規定より次を優先すること: クイックモードを既定とし、フルモードはユーザーが「しっかり」「時間をかけてよい」などと明示した場合だけ使い、対外文書であることを理由に自動でフルへ切り替えない（dotfiles ADR-0066）
- 敬語・挨拶・クッション言葉（「いかがでしょうか」など）について 2 つのスキルの指摘が食い違う場合は、`japanese-business-writing` の判断を優先すること

# Plan 共通ルール

- Phase を含む Plan では、各 Phase ごとに使用する Skill を明示し、使用しない Phase は `なし` と明記すること
- Phase を含む Plan は、実行時に途中確認を前提にせず完走できる粒度で提示し、Phase 提示後は不測の事態がない限り追加許可を求めず停止せず最後まで進めること。ただし、既存 Skill や repo ルールで明示された事前確認は例外として維持すること
