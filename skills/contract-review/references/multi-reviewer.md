# multi モード

プロファイルの `review_mode` が multi を許すとき、またはユーザーが明示したときに使う。repo の AI 利用方針が単独レビューを定めている場合は、ユーザーが求めても multi にせず、その旨を伝える。

## レビュアーの構成

- モデル・effort・provider は `agent-orchestrator/rules/model_registry.yaml` で解決する。この skill に書かない
- 契約レビューは判断を伴う執筆なので、registry の tier `A` を既定にする。金額が大きい、条項が複雑、相手方との力関係に懸念があるなど失敗コストが大きい場合は親が `S` を選ぶ
- registry で route に使わないと決めた provider は使わない

| レビュアー | 実行経路 | 期待 artifact |
|---|---|---|
| Claude | Agent tool の subagent（親の Claude 列） | `.context/contract-<略称>/claude-review.md` |
| Codex | `codex-cli-runner` skill（registry の Codex 列） | `.context/contract-<略称>/codex-review.md` |

- 親（司令塔）は統合と出力だけを担う。親と同じモデルであっても、親がレビュアーを兼ねない
- `codex` が PATH に無い、認証が通らない、またはユーザーがスキップを指示した場合、そのレビュアーは「未実行」とする。モードの呼称を曖昧にせず、実際に走ったレビュアー数で `single` / `multi-2` と書く

## レビュアーへの指示（source prompt に書く内容）

```text
あなたは日本の契約書レビューの専門家です。次のファイルを読み、契約書をレビューしてください。

- 契約書本文: .context/contract-<略称>/ocr.txt
- 当社の立場: <甲・委託側 | 乙・受託側>
- 共通チェックリスト: <skill-dir>/references/checklist.md
- 追加チェック（該当時のみ）: <プロファイルの extra_checklists>

出力:
- 指摘を高 / 中 / 低に分け、各指摘に条項番号・問題点・修正提案を付ける
- 欠落条項を挙げる
- 日本語で書き、<期待 artifact のパス> に保存する

禁止:
- 他のレビュアーの出力を読まない
- 統合判定をしない、最終レポートを編集しない
```

本文やプロンプトはファイルで渡し、コマンド引数に展開しない。

## 統合

| 分類 | 条件 | 信頼度 | 扱い |
|---|---|---|---|
| 全員一致 | 全レビュアーが指摘 | 高 | 優先対応 |
| 単独指摘 | 1 レビュアーのみ | 要確認 | 見落としの可能性として親が検討する |
| 評価相違 | 同じ条項で結論が分かれる | 要検討 | 弁護士相談の候補 |

### プロファイル基準による上書き（必須）

外部レビュアーは立場ごとの標準判断（position-stances.md）とプロファイルの `house_rules` を知らずに指摘する。親は統合時に全指摘をこれらと突合し、衝突した指摘は当社基準の側を採用する。

- 衝突した指摘は報告の「評価が分かれた項目」に載せ、採用しなかった理由と根拠の基準を書く。黙って削除しない
- 典型例: 受託側で損害賠償上限の双務化を求める指摘、請負契約で任意解除権の相互化を求める指摘
