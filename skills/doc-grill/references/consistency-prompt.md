# 整合レビュー依頼文テンプレート

Grill → 裁定 → 反映のあとに使う。〔〕を埋めて、model_registry で解決した整合レビュアー（既定は `reviewer_tech`）に渡す。読み取り専用で、成果物は 1 ファイルだけ書かせる。

---

あなたは〔自社名〕の社内レビュアーです。〔文書名〕が関連文書すべてと整合しているかを検証してください。読み取り専用で、リポジトリのファイルは編集しないでください。成果物は指定の path に 1 ファイルだけ書いてください。

## 読むファイル

1. 検証対象: 〔文言の正本の path〕（ページ・節の単位を明記）
2. 同時に送る文書（質問リスト・案内文・送付メールなど）: 〔path または なし〕
3. 対応表・差分表: 〔path または なし〕
4. 送付済みの文書: 〔path または なし〕
5. 後続の合意（返信など）: 〔path または なし〕。送付済み文書と食い違う場合は、こちらを優先する
6. 相手から受け取った文書: 〔path または なし〕
7. 経緯（会議日時・期限などの確定事実を含む）: 〔path〕
8. 直前の Grill 結果と裁定表（採用・保留・却下の区分）: 〔path〕
9. 文言ルール: 〔path〕

## 検証の観点（すべて具体的な引用で示す）

A. 検証対象と同時送付文書の整合: 対応表の主張の正否、進め方（順番・時間配分）の一致、宿題の重複、用語の統一。
B. 検証対象と送付済み文書・後続合意の整合: 費用、支払、期間、解約、開始日、提供形態、役割分担、責任分界、自社が作る成果物、実施主体、データの扱い、到達イメージ。
C. 検証対象と相手の文書の整合: 相手の各論点に、文書のどこかで答えているか。
D. 検証対象の内部整合: 矛盾する記述、粒度の揺れ、議事順とページ順、数値の一致。
E. 裁定で「採用」とした指摘が本当に反映されているか。「保留」の項目が確約の表現になっていないか。
F. 同時送付文書と確定事実（会議日時、期限、過去の発言）の整合。

## 成果物

〔.context/<task>/grill-rN/consistency.md の絶対 path〕に日本語の Markdown で書く。先頭に Front Matter（`task` / `phase_or_step` / `created_at`）。構成:

1. 総評（整合が取れているか、残る不整合の件数と深刻度）
2. 不整合一覧（表）: ID / 深刻度（Critical / Major / Minor） / 対象 / 内容 / 根拠の引用（両側） / 修正案（差し替え文言まで）
3. 整合を確認できた項目（観点ごとに 1 行ずつ）
4. 対応表・差分表の誤りと抜け

## 制約

- 書いてよいファイルは成果物だけ。git 操作をしない。再委譲しない
- 推測で事実を作らない。文書に無い事実は「文書上は未確認」と書く
- 完了したら、成果物の path と深刻度別の不整合件数だけを短く報告する
