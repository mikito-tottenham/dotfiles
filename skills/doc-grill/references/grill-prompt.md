# 依頼: 〔文書名〕の Grill（徹底的な批判レビュー）

あなたは〔自社名〕の社内レビュアーです。次の文書を Grill してください。Grill とは、送付・投影・提出の前に、読み手から突っ込まれる点、約束しすぎている点、矛盾、曖昧さ、事実として不正確な主張を、遠慮なく洗い出す作業です。褒める必要はありません。

## 背景

- 文書の目的と読み手: 〔誰に、何を判断してもらう文書か。対外か社内か〕
- 読み手の属性と、こちらとの関係: 〔専門性、懸念、現状。契約条件・提供形態・役割分担の要点〕
- これまでの経緯: 〔相手へ送った文書と、相手から受け取った文書の要点〕
- 案件の位置づけ: 〔例: 実績づくりを優先し条件は柔軟、など〕

## 読むファイル（読み取りのみ。編集しない）

1. Grill 対象（文言の正本）: 〔path〕
2. 相手から受け取った文書: 〔path または なし〕
3. 送付済みの文書（提案書・返信など）: 〔path または なし〕
4. 差分表・対応表: 〔path または なし〕
5. 社内の既存見解（技術方針・事業方針の根拠）: 〔path〕
6. 文言ルール・機密の境界: 〔path〕
7. 経緯: 〔path〕
8. （R2 以降）前ラウンドの裁定表: 〔path〕

## 観点

A. 読み手の視点（〔読み手のプロフィール〕）: 納得できない点、投げてくる質問、「答えになっていない」と感じる箇所、読み手の問いに答えていない箇所。立場の違う読み手が複数いる場合は、立場ごとに最も強い反論を 1 つずつ挙げる。
B. 自社の事業・契約の視点: 契約条件や提供範囲を超える約束、送付済み文書との不整合、自社が作る成果物の膨張、文言ルール違反。
C. 事実・技術の正確性: 製品・サービス・制度・データの扱いに関する主張の誤り、過剰な断定。公式資料で確かめられる事実は確かめ、出典を示す。確かめられないものは「要確認」とし、断定しない。
D. 構成・論理: 順序、重複、抜け、詰め込みすぎ、使う場面（会議の時間枠、読む時間）に合わない箇所。
E. 差分表・対応表そのものの見落とし・誤り。
F. （R2 以降）前ラウンドで「採用」とした指摘が反映されているか。反映によって新しい矛盾が生まれていないか。

数値は暗算しないこと。文書中の数値・合計・比率・日付計算は script で再計算し、検算表にまとめること。

## 成果物

〔.context/<task>/grill-rN/result.md の絶対 path〕に日本語の Markdown で書く。構成:

1. 総評（3〜5 行）と判定: そのまま使える / 修正すれば使える / 作り直し のいずれか、理由付き
2. 指摘一覧（表）: ID / 深刻度 / 対象（ページ・節） / 指摘 / 根拠（どのファイルのどの記述と矛盾・不足するか、引用付き） / 修正案（差し替え文言まで）
   - Critical: 読み手の信頼を損なう、契約・法務・金銭のリスクがある、事実が誤っている
   - Major: 修正を強く勧める。読み手の判断に影響しうる
   - Minor: 表現や好みの範囲
3. 検算表: 数値 / 文書上の値 / 再計算した値 / 一致・不一致 / 計算方法
4. 読み手が投げてきそうな質問 10 個と、現状の文書では答えられない・弱い点
5. 送付済み文書との不整合の一覧
6. 差分表・対応表の見落とし・誤り
7. ユーザーまたは責任者の裁定が必要な論点（文書側では決められないもの）

## 制約

- 書いてよいファイルは result.md と、検算に使う一時 script だけ。他のファイルを変更しない。git 操作をしない
- サブエージェントや別のエージェントへ再委譲しない。自分で全文を読んで回答する
- 根拠はページ・節番号と引用で示す。推測で事実を作らない
- 完了条件: result.md が上の 7 節を満たして書かれていること
