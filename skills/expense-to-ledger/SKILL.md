# expense-to-ledger

経費の証憑を集めて Drive に格納し、会計システム（マネーフォワード クラウド会計 / freee）に取り込める形にする。工程は会社に依らず共通で、会社ごとの値は repo 側の **経費プロファイル** から読む。

## 守ること

- 勘定科目・貸方・税区分は AI が確定してよい領域ではない。推定はすべて「仮定」として明示し、取り込み前に顧問税理士などの確認を推奨する
- 会計システムへの書き込みは、対象・件数・金額合計・勘定科目を提示してユーザーの明示承認を得てから、1 操作ずつ実行する。詳細は [references/ledger-write-safety.md](references/ledger-write-safety.md)
- 証憑は削除しない。対象外や重複は退避フォルダへ移すかゴミ箱に入れ、完全削除はしない
- 円換算額が確定できない外貨建て証憑を推定レートで仕訳に入れない
- フォルダ ID・勘定科目コード・口座などの会社固有値を、この skill にも git 管理ファイルにも推測で書かない。プロファイルに無い値はユーザーに確認する
- 取得した明細の生データは `.context/` に置き、git 管理ファイルには概要の数値と手順だけを残す

## Step 0: プロファイルとアカウントを確認する

1. repo の `AGENTS.md` が指す経費プロファイルを読む。キーは [references/repo-profile.md](references/repo-profile.md)
2. 対象会社に対応する `gws-account` profile で `gws-account <profile> auth status` を実行し、`user` が目的の組織か確かめる。MCP コネクタは別アカウントに接続していることがあるので、Drive / Gmail の操作は `gws-account` を使う（`gws-cli-runner` skill）
3. 会計 MCP を使う場合は、事業所確認（MF: `mfc_ca_currentOffice`、freee: 事業所取得）で目的の事業所であることを確かめる

## Step 1: 証憑を集める

| 入口 | やり方 | 注意 |
|---|---|---|
| メールの領収書 | Gmail を `in:anywhere` で検索し、送信者・件名・本文で領収書だけに絞って PDF 化する | タグ前提の絞り込みはしない。本文フィルタの誤爆はフィルタを緩めず個別救済する。受信アカウントと Drive のアカウントが違う場合は、送信元アカウント内で完結する仕組み（Apps Script など）と共有フォルダに分ける |
| 紙の領収書の写真 | 親が画像から日付・金額・店名・宛名を読む → `.context/<task>/paper-receipts/` にコピー → `sips` で回転 → 回転後の画像を開いて読取値を再確認 → `sips -s format pdf` で PDF 化 | 再確認を省略しない。宛名違い・判読不能は要確認に回す |
| ローカル PDF・スキャン | ファイル名や本文から日付・金額・ベンダーを読む。スキャンで読み取りが要るものは `pdf-extract` skill を使う | 読めない値は推測で埋めない |

- 処理は冪等にする（処理済み ID の記録、再実行で重複しない）。途中で止まる仕組みでは「PARTIAL → 再実行」を正常系として扱う
- 10 件以上の反復は進捗ログ付きスクリプトに切り出す。ただし紙領収書の読取と再確認は自動化しない

## Step 2: 命名して格納する

- ファイル名: `<ベンダー>_<YYYY-MM-DD>_¥<金額>_<識別子>.pdf`。外貨は原通貨表記のまま（例: `$26.94`）。日が特定できないときだけ `<ベンダー>_<YYYY-MM>_¥<金額>.pdf` とし、要確認に載せる
- 日付は **利用日** 基準（乗車日、宿泊日、注文日など）。受信日・決済日ではない。月初に受信したものは前月末の利用を疑う
- 格納先はプロファイルのフォルダ ID 表から引く。名前検索で探さない。表に無い月はフォルダを作ってから表に ID を足す（表の更新は repo 側の変更として扱う）
- 重複判定は **全月フォルダとアーカイブの名前の和集合** で行う。単一フォルダだけで判定すると、移動済みのファイルを再コピーして二重化する
- 二重化したら同名グループごとに最古の 1 件を残し、残りをゴミ箱へ入れる。完全削除はしない
- 経費対象外の証憑は削除せず、プロファイルの対象外フォルダへ移す

## Step 3: 漏れを監査する

- メール側: アーカイブ・ゴミ箱・迷惑メールを含めて走査し、処理済み記録と突合する
- 外部履歴: 利用履歴を出せるサービス（配車、EC など）は、金額と利用日をキーに Drive 側と突合する。履歴にあって Drive に無いものは MISSING、逆は説明できるか（キャンセル料、重複受領など）を確認する
- Drive 側: 同名重複 0 件、ファイル名の日付と格納月の一致、入口別の件数が取り込みログと一致
- ゴミ箱で完全削除されたメールはメール側の走査では見つからない。外部履歴を持たない証憑（紙など）について「漏れは無い」と言わない

## Step 4: 仕訳データを作る

出力は必ず 3 点セットにする。

| ファイル | 内容 |
|---|---|
| 仕訳データ（CSV など） | 会計システムの取り込み仕様に合わせる。[references/journal-import.md](references/journal-import.md) |
| `要確認リスト.csv` | 仕訳から外した証憑と、計上したが仮定に依存する行 |
| `README_前提と要確認.md` | 置いた仮定、推定ルール、検算結果、未検証事項 |

- 既存の経費集計（会社が作った勘定科目・税区分付きの表）がある行は、その値を採用し表記だけ整える。AI が上書きしない
- 勘定科目の推定はプロファイルの `account_rules` に従う。判別できないものは仮置きして要確認に載せる
- 貸方（立替なら役員借入金・未払金、法人カードなら未払金など）はプロファイルの `credit_assumption` に従い、README に仮定として書く
- 重複は「日付 ±1 日かつ金額一致」を候補とし、同一ベンダー・同日・同額の集約は別決済の可能性があるので要確認に載せる
- 検算: 行数（入口別内訳）、借方合計、勘定科目別の行数と金額、税区分別の行数、対象期間、借貸一致

## Step 5: 取り込み前の検証ゲート

- 会計システムに入れる前に dry-run の検証を通す。プロファイルにマスタ（勘定科目・部門・税区分）があれば、未知の科目・部門を NG として止める
- 合計の突合に許容差を設ける場合はプロファイルに書かれた値を使う
- NG が 1 件でもあれば書き込みに進まない。書き込みはスクリプトでも明示フラグ（例: `--write`）を付けたときだけにする
- サブエージェントに作らせた場合も、親が CSV の実体を数えて README と突き合わせる。README の記述を信じない

## Step 6: 会計システムに反映する

- 既定は「ユーザーが会計システムの画面で CSV を取り込む」。AI は取り込み用ファイルと手順を渡す
- MCP / API で書き込む場合は [references/ledger-write-safety.md](references/ledger-write-safety.md) の確認手順を必ず通す
- 反映後は読み取り系の操作（仕訳・取引の一覧）で件数と合計を照合し、結果を `.context/<task>/` に記録する

## 完了条件

- 証憑が命名規約どおりに格納され、同名重複 0 件、日付と格納月が一致している
- 漏れ監査の結果と「検出できない範囲」を報告した
- 3 点セットが揃い、検算結果が README と CSV 実体で一致している
- 会計システムへの書き込みをした場合は、承認の記録と反映後の照合結果がある
