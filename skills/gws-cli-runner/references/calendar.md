# カレンダー操作リファレンス

本人が複数の組織・アカウントのカレンダーを併用している前提で、空き枠の算出から返信文案・予定作成までを扱う。読み取り（空き枠の算出、ACL の確認）は確認なしで進めてよい。外部に見える変更（メール送信、予定作成・招待、予約ページの保存、共有設定の変更）は、内容を提示してユーザーの明示承認を得てから 1 操作ずつ実行する。

正本の参照先（ここに写さない）:

- 会社・組織とアカウントの対応、MCP コネクタがどのアカウントに接続しているか: 作業ルートの `AGENTS.md`（「アカウント境界」節）
- profile 一覧、再認証、カレンダー共有 ACL（`calendar-acl plan` → `apply`、外部宛の実効 role 確認）: [account-profiles.md](account-profiles.md)

## Step 0: 対象とアカウントを決める（preflight）

1. 依頼から参加者と、それぞれの予定がどのカレンダーにあるかを整理する。本人については、関係する組織のカレンダーをすべて対象にする
2. 正本の対応表から、各カレンダーを読む profile を決める。迷ったらユーザーに確認する。MCP のカレンダーコネクタは接続アカウントが限られるので、横断の算出には使わない
3. 使う profile ごとに `gws-account <profile> auth status` を実行し、`user` が目的の組織であること、token が有効であることを確かめる。失効していたら SKILL.md の Recovery Runbook で同じ profile を復旧する。別の profile へ黙って切り替えない
4. 相手方（社外の人）のカレンダーは、`freeBusyReader` 以上で共有されていない限り読めない。読めない相手の予定は推測しない

## Step 1: 共通の空き枠を出す

```bash
python3 <skill-dir>/scripts/free_slots.py \
  --source <profile-A> --source <profile-B>:primary --source <profile-A>:<共有されたカレンダー ID> \
  --from YYYY-MM-DD --to YYYY-MM-DD --start-hour 10 --end-hour 18 --slot-min 30 --buffer-min 15 \
  > .context/<task>/free-slots.md
```

- `--source <profile>` はその profile が購読している全カレンダー（祝日を除く）、`:primary` は主カレンダーだけ、`:<ID>` は特定のカレンダー（freeBusyReader 共有を含む）
- 内部では profile ごとに `calendar calendarList list` と `calendar freebusy query`（50 件ずつ）を呼ぶ。読み取りのみ
- 出力の「参照したカレンダー」表を必ず確認する。exit 3 は参照できなかったカレンダーがあることを示す（枠そのものは出力される）。exit 1 は gws の実行失敗
- 回答には「どのカレンダーを参照できたか / できなかったか」を必ず書く。相手方のカレンダーを参照できていない場合は「こちら側の空きのみ」と明記し、相手の空きとして提示しない
- 移動時間・対面の前後余白が要る場合は `--buffer-min` で足す。オンラインと対面で分けたいときは条件を変えて 2 回出す
- カレンダー ID や予定の中身を git 管理ファイルに書かない。結果は `.context/<task>/` に置く。script はカレンダー ID のローカル部を `***@domain` に伏せて出力する

## Step 2: 予約ページ・共有設定を調整する（必要な場合）

Google カレンダーの予約スケジュール（予約ページ）は「空き確認の対象にしたカレンダーのどれかが埋まっていれば枠を出さない」。複数組織のカレンダーを対象に入れれば、本人の全予定を反映した枠になる。別組織のカレンダーは、予約ページの所有アカウントへ `freeBusyReader`（予定の時間枠のみ表示・詳細は非表示）で共有すれば足りる。主催者（招待の送信元）は所有アカウントに固定されるので、名義を使い分けたい場合は名義ごとのアカウントで予約ページを 1 本ずつ作り、空き確認の対象カレンダーは共通にする。

### 制約

| 制約 | 内容 |
|---|---|
| 共同主催者は同一ドメインのみ | 外部ドメインのユーザーは共同主催者に追加できない。社外の人と空きを重ねる目的には使えない |
| 主催者は変更できない | 予定の organizer は作成先カレンダーの所有者に固定（API でも変更不可） |
| 予約成立時の予定は主催者のカレンダーにだけ入る | 空き確認の対象カレンダーには入らず、同席者にも招待は届かない。同席者が必要ならゲスト追加が要る |
| 予約ページは公開 | リンクを知っていれば誰でも予約できる。組織内限定にはできない。配布先で管理する |
| 設定の API が無い | 予約ページの作成・変更は画面操作のみ。ブラウザ操作で行う場合も保存の前に変更内容を提示して承認を得る。ユーザー本人に操作してもらう方が早い場合はそう案内する |
| 共有は一方向 | アカウント A へ共有しても B からは見えない。所有アカウントごとに共有と購読が要る |
| iCal の秘密アドレスは使わない | 予定の詳細を含むため、空き時間だけの共有にならない |
| プラン | 予約ページの機能はアカウントのプランに依存する。相手方のプランが対応しているかは確認する |

### 手順

1. 空き確認に入れたいカレンダーのアカウントで、予約ページ所有アカウントへ「予定の時間枠のみを表示」（`freeBusyReader`）で共有する。共有設定の変更と外部宛の実効 role 確認は [account-profiles.md](account-profiles.md) の「カレンダー共有 ACL」に従う。期待した role より強い権限が付いていたら、apply の結果を成功扱いにせず報告する
2. 予約ページ所有アカウントで、共有されたカレンダーを購読する
3. 予約ページの編集画面で「空き状況を確認するカレンダー」に追加して保存する。保存の前に、追加・削除するカレンダーと受付時間帯の変更内容をユーザーに提示して承認を得る
4. 確認: `scripts/free_slots.py` を予約ページと同じ条件（受付時間帯、枠の長さ、対象カレンダー）で実行し、公開ページに出る枠と大きくずれないことを確かめる。受付時間帯を設定しても、実際に出る枠はかなり少なくなることがある

### 同席者への招待

予約成立後に同席者を自動でゲスト追加する仕組みは標準機能に無い。必要なら、主催アカウント側で動く定期実行のスクリプト（Apps Script など）で補う。空き判定には関与させず、招待の追加だけを担わせる。設置・変更は外部への招待送信を伴うので、ユーザーの承認を得てから行う。

## Step 3: 返信文案を作る

- 候補は 3〜5 枠を目安に、日付・曜日・時刻・タイムゾーン・所要時間・形式（オンライン / 対面）を書く。予約ページを使う場合はリンクを案内する
- 敬語と構成は `japanese-business-writing` に従う
- 送るのはユーザー。下書きをメールボックスに作るのも、ユーザーが求めた場合に限る。その場合も送信元アカウントが目的の組織であることを確かめる

## Step 4: 予定を作る（承認後）

- 「私発信で」「当社名義で」など主催者の指定があれば、その名義のアカウント（profile）で作る。主催者は作成したカレンダーの所有者に固定され、後から変えられない
- 作成前に、主催アカウント、件名、日時、参加者、会議リンクの有無、招待メールを送るかを提示して承認を得る
- 作成後は予定を取得し直して、日時・参加者・会議リンクが意図どおりかを確認する。リスケは既存予定の更新として扱い、新規作成と既存予定の削除を勝手に組み合わせない

## やらないこと

- 参照できなかったカレンダーの予定を「空いている」とみなす
- 認証が切れた profile の代わりに、別アカウントや MCP コネクタで黙って算出する
- 承認なしにメール送信、予定作成・更新、予約ページの保存、共有設定の変更をする
