# 予約ページを複数組織で使う

## 構成の考え方

- 予約ページは「空き確認の対象にしたカレンダーのどれかが埋まっていれば枠を出さない」。複数組織のカレンダーを対象に入れれば、本人の全予定を反映した枠になる
- 別組織のカレンダーは、予約ページの所有アカウントへ `freeBusyReader`（予定の時間枠のみ表示・詳細は非表示）で共有すれば足りる。予定名や参加者は渡らない
- 主催者（招待の送信元）は予約ページの所有アカウントに固定される。名義を使い分けたい場合は、名義ごとのアカウントで予約ページを 1 本ずつ作り、空き確認の対象カレンダーは共通にする

## 制約

| 制約 | 内容 |
|---|---|
| 共同主催者は同一ドメインのみ | 外部ドメインのユーザーは共同主催者に追加できない。社外の人と空きを重ねる目的には使えない |
| 主催者は変更できない | 予定の organizer は作成先カレンダーの所有者に固定（API でも変更不可） |
| 予約成立時の予定は主催者のカレンダーにだけ入る | 空き確認の対象カレンダーには入らず、同席者にも招待は届かない。同席者が必要ならゲスト追加が要る |
| 予約ページは公開 | リンクを知っていれば誰でも予約できる。組織内限定にはできない。配布先で管理する |
| 設定の API が無い | 予約ページの作成・変更は画面操作のみ |
| 共有は一方向 | アカウント A へ共有しても B からは見えない。所有アカウントごとに共有と購読が要る |
| iCal の秘密アドレスは使わない | 予定の詳細を含むため、空き時間だけの共有にならない |
| プラン | 予約ページの機能はアカウントのプランに依存する。相手方のプランが対応しているかは確認する |

## 手順

1. 空き確認に入れたいカレンダーのアカウントで、予約ページ所有アカウントへ「予定の時間枠のみを表示」で共有する
   - 本人のアカウント間の共有は `calendar-acl`（policy を 1Password から復元）で宣言的に管理しているので、`calendar-acl plan` → 承認 → `calendar-acl apply` で行う
   - 外部宛の共有は、変更の前後に `gws-account <profile> calendar acl list` で実効 role を確認する
2. 予約ページ所有アカウントで、共有されたカレンダーを購読する
3. 予約ページの編集画面で「空き状況を確認するカレンダー」に追加して保存する。保存の前に、追加・削除するカレンダーと受付時間帯の変更内容をユーザーに提示して承認を得る
4. 確認: `scripts/free_slots.py` を予約ページと同じ条件（受付時間帯、枠の長さ、対象カレンダー）で実行し、公開ページに出る枠と大きくずれないことを確かめる。受付時間帯を設定しても、実際に出る枠はかなり少なくなることがある

## 同席者への招待

予約成立後に同席者を自動でゲスト追加する仕組みは標準機能に無い。必要なら、主催アカウント側で動く定期実行のスクリプト（Apps Script など）で補う。空き判定には関与させず、招待の追加だけを担わせる。設置・変更は外部への招待送信を伴うので、ユーザーの承認を得てから行う。
