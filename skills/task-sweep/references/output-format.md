# artifact と報告の書式

## 共通の Front Matter

```yaml
---
task: task-sweep
phase_or_step: 04-report        # 01-preflight / 02-candidates-<source> / 03-resolution / 04-report
created_at: 2026-10-03T15:00:00+09:00
period: 2026-09-03..2026-10-03  # 対象期間
input_list: <入力のタスク一覧ファイルのパス、無ければ none>
---
```

## 02-candidates-<source>

候補 1 件につき、タスクの要旨、関係者、日付、出典、そのソースから見えた状態の手がかり（依頼 / 約束 / 着手 / 完了報告 / 取りやめ）を書く。この段階では状態を確定させない。

## 03-resolution

名寄せの結果（どの候補を同じタスクとみなしたか）と、各タスクに 5 区分のどれを付けたか、その理由を書く。食い違う証拠は両方を残す。

## 04-report

タスクごとに 1 ブロック。入力一覧の項目は入力側の ID を使い、新規候補には `N-01` から順に振る。

```markdown
### T-03 〇〇の申請
- 状態: 進行中（担当者 A が書類を回収済み。提出は未確認）
- 根拠:
  - Slack #backoffice 2026-09-28 担当者 A「書類そろいました」 <permalink>
  - Gmail 「〇〇 受付のお知らせ」は期間内に見つからない（in:inbox / in:sent を「〇〇」で検索）
- 次のアクション / 担当: 提出（担当者 A）
- 期限: 2026-10-10（出典: 〇〇メール 2026-09-20）
```

出典の書き方:

| ソース | 書き方 |
|---|---|
| Slack | permalink |
| Chatwork | ルーム名 + メッセージ ID |
| Gmail | 件名 + 日付（送受信の別） |
| Calendar | 予定名 + 日付 |
| Drive | ファイル名（共有ドライブ名・フォルダ）+ 更新日 |
| git | `origin/main:<path>:<line>` または commit hash |

期限や担当が分からないときは空欄にせず「不明」と書く。

報告の末尾に必ず次の 3 節を置く。台帳を持たないため、次回の実行者が取りこぼしを疑えるのはこの記録だけである。

1. **ソース不通**: ソース名、失敗の内容、その影響で `判定不能` になったタスク ID
2. **探したが見つからなかった範囲**: ソースごとの検索条件と期間（例: Chatwork の 100 件上限で未確認になった期間）
3. **新規候補**: 入力一覧に無かった未完了タスクの一覧（ID・状態・根拠を上と同じ形で）

`.context/` に生データを保存した場合は、その場所と「不要になったら削除」を最後に書く。
